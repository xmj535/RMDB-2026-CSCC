# Performance Notes

本文档总结公开版本中可以从实现直接观察到的主要性能优化方向。这里重点记录优化原理，不复述比赛评分规则，也不把特定测试用例作为设计依据。

## 1. Scan 路径选择

Snapshot Isolation 下，在存在合适索引并满足计划条件时可以使用 IndexScan，减少大表查询的扫描范围。

Serializable 模式需要同时维护 SSI 读依赖 / 谓词语义。某些索引路径会改变可观察到的读集合，因此 Planner 对该模式采取更保守的路径选择，以正确性优先。

## 2. Join 策略

纯 Nested Loop Join 在大输入上可能产生 `|outer| × |inner|` 级别的行访问。Planner 对大规模连接启用更合适的路径，包括 Hash Join、分块策略和可利用索引时的 Index Join，同时尽量保持小查询计划稳定。

## 3. B+ Tree 扫描

索引扫描会缓存当前叶子页并维护严格的 pin / unpin 生命周期，减少逐记录 `fetch_node`、对象创建和页固定操作。

同时对并发 split / merge 或游标越界等情况进行防御式处理，避免异常索引位置导致服务端进程退出。

## 4. Buffer Pool 与 WAL

Buffer Pool 的容量直接影响大表查询和恢复阶段的缺页行为。实现中通过回调确保脏数据页刷盘前先完成必要的日志持久化，满足 WAL 的 write-ahead 约束。

## 5. 事务与 MVCC 内存控制

长时间运行和大规模自动提交会产生大量事务对象、版本信息和 SSI 元数据。实现包含：

- 已结束事务的生命周期回收；
- watermark 驱动的历史版本回收；
- SSI 已完成事务状态清理；
- 对极端大读集进行有界控制；
- 在适当时机归还可释放的堆内存。

这些措施用于抑制长期运行时 RSS 持续增长。

## 6. Recovery

恢复过程采用分阶段、流式日志扫描，避免把大日志的全部记录长期保存在内存中。

静态检查点记录可让恢复从更靠后的日志位置开始，并在检查点创建期间协调事务与数据页状态，从而兼顾恢复正确性和恢复时间。

## 7. Benchmark 可复现性

比赛环境中的完整负载、数据规模和评测工具并未全部纳入公开仓库。因此，本仓库不声明 GitHub 用户在任意硬件上可以复现原比赛排名或全部性能数字。

如需比较优化效果，建议固定以下条件：

- 编译器与编译参数；
- 数据集与初始化状态；
- 隔离级别；
- 并发度；
- Buffer Pool 配置；
- 每轮测试前的数据库 / OS cache 状态；
- 相同 SQL 与相同统计口径。
